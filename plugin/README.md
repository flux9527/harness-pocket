# dsh-mobile-console

在手机浏览器上管理 DSH：**看状态、批审批、发消息、答提问**。人离开电脑时，不用再跑回来点那个弹窗。

它是一个 DSH / Cordis 插件，自己在局域网里起一个小服务（默认 `0.0.0.0:8799`），
手机连上同一个 Wi-Fi 打开一个链接就能用。

**也有 Android 应用版本**（[`../android`](../android)，基于 Capacitor）：
息屏后连接不断，并发送 **Android 16 原生 Live Updates 通知**——通知上直接看智能体状态与余额、
直接点「允许 / 拒绝」。构建与安装见 [android/README.md](../android/README.md#构建)。

```
手机浏览器 ──HTTP/SSE──▶ 插件（0.0.0.0:8799）
                            │
                            ├─ approval/request       ◀── 审批弹窗
                            ├─ tools/execute          ◀── ask_user_question
                            ├─ session/event          ──▶ 状态、回复、动态
                            └─ agent.assistant-stream ──▶ 运行中
```

---

## 30 秒上手

1. **装**（见下方「安装」），然后重启 DSH 或让它热重载。
2. 在 DSH 里执行 `/mobile on` —— 让你**当前这个会话**接受手机接管。
3. 执行 `/mobile url`，把输出的地址发到手机上打开（或在电脑浏览器打开后扫二维码，见 `/mobile qr`）。
4. 手机上确认页面能打开、能看到会话列表，就通了。

> 只做第 2 步的会话会被接管。**没武装的会话，行为与没装插件时完全一样。**

## 四种能力

### 1. 看状态

- 会话列表：运行中 / 空闲 / 已离线，是否武装，最近活动时间。
- 正在跑哪个会话、跑了多久、最近一次输出。
- 动态流：审批、提问、回复、错误、注入，按时间倒序。

运行状态不是靠 `agent/status` 得到的 —— **当前构建从不派发这个事件**（实机探针确认：注册了监听一条都收不到）。
真正的信号是 `session/event` 的 `step/*`、`tool/*`、`assistant/*`、`user/*`（在回合内）与 `turn/end`（回合结束），
外加最灵敏的 `agent/assistant-stream`（正在流式输出）。`agent/status` 的监听仍然保留，将来构建真的派发它时会自动成为权威来源。

### 1.5 看余额

快照里带一份账户余额（`balance` 字段），`/mobile status` 也会显示。Android 端的 Live Updates 通知会把它一起画出来。

余额取自宿主自己的 `ctx.get('deepseekAccount').getBalance()` —— 插件就跑在宿主进程里，
凭据只对 Host 消费者开放，这是唯一正规的通道，比自己去拼第三方 API 可靠得多。
账户服务不存在、未登录、查询失败、调用抛异常，这四种情况都只影响那一行文字，不影响插件其它功能。

### 2. 批审批

审批请求会实时推到手机上，点「允许 / 拒绝」。允许等于在电脑上点允许 —— 需要越权的操作会**真的执行**。

- 只在「会话已武装」**且**「手机在线」时才接管，否则一律走原生链路。
- 手机没连上时绝不接管：否则一个没人在看的待办会把整个回合卡住。
- 默认 120 秒没人答就回落给原生链，回合照常继续。

### 3. 发消息

手机上输入一段话发给任意会话，等于以用户身份注入一条消息，并等它跑完、把回复回传到动态流。

目标会话**正忙时也能发**——消息会排队，等当前这一轮结束再跑。这里曾经有个隐蔽的坑：
只 `await whenIdle()` 的话，它会在**当前这一轮**结束时立刻兑现，那时注入的消息还排在队里，
抓到的会是上一轮的输出，手机上就显示一条张冠李戴的"回复"。现在的做法是等日志里真的出现
我们注入的那条 `user/message`，确认"轮到我们了"再去取结果；`bridge.test.mjs` 里有一条专门
复现这个时序的用例（并且验证过：把修复退回去，这条用例会失败）。

### 4. 答提问

`ask_user_question` 的选项会推到手机上，可以单选、多选、也能自己填一段文本。

> 实机结论：当前构建里 `ask_user_question` 是通过 **`tools/execute`** 被拦到的（日志里 `via=tool`），
> `user-questions/request` 那条路走不到。两条路都实现了，所以将来哪条生效都不会失效。

## `/mobile` 命令

| 命令 | 作用 |
| --- | --- |
| `/mobile on` | 让当前会话接受手机接管（子会话跟随父会话） |
| `/mobile off` | 关掉当前会话的接管（显式关掉后不会再被自动武装覆盖） |
| `/mobile status` | 服务状态、端口、在线手机数、配对地址、本会话是否武装 |
| `/mobile url` | 只输出配对地址，方便复制 |
| `/mobile qr` | 在终端里画一个 ASCII 二维码 |
| `/mobile help` | 帮助 |

## 在 DSH 界面里管理（设置 → 手机控制台）

按方式二 / 方式三装成包之后，DSH 的**设置**面板里会多一页「手机控制台」，不用敲命令：

- **总开关**：一键开启 / 关闭。关掉时**真的停掉监听**（手机连不上）、正在等的审批与提问
  立刻回落给电脑上的原生弹窗，而不是让人干等到 120 秒超时。会话表刷新不停，所以这一页仍然有状态可看。
- **状态**：监听端口、在线手机数、**账户余额**、待办数。
- **配对地址**：整段可复制，右边是二维码；关掉时不显示地址（端口没在听，给了也连不上）。
- **会话列表**：每个会话一个「接管 / 取消接管」，等价于在那个会话里执行 `/mobile on` / `off`。
- **重新生成令牌**：会让所有已配对的手机（包括装好的 APK）立刻失效，需要二次确认。

### 它是怎么接上去的

- **浏览器半边**（`client.js`）：用 `window.__ModuleLoader__.load` 注册进 DSH 的 `settings.section`
  插槽，只依赖 shell 自带的 `react`，颜色全取 DSH 主题变量，亮 / 暗切换正常。
- **宿主半边**（`src/desktop.js`）：通过 `ctx.inject(['webServer'], …)` 注册同源路由
  `/api/mobile-console/*`。**不走手机那个 8799 端口**——从 `127.0.0.1:19387` 去访问局域网网卡地址
  是跨域，会被浏览器拦。
- **安全**：这些路由的前缀比内核的 `/api` 更长，而 webServer 是**最长前缀优先**，所以它们跑在内核
  准入检查**之前**。不自己加围栏的话，任何能访问回环地址的东西都能读到配对令牌（等于手机控制台的
  完整控制权）。因此每个请求先过两道防线：优先用宿主 `connection` 服务的准入结论，没有该服务时
  退回结构等价的本地围栏（只允许回环 Host 防 DNS 重绑定、拒绝 `Sec-Fetch-Site: cross-site`、
  `Origin`/`Referer` 必须与 `Host` 同源）。裸 HTTP 客户端拿不到 GUI 的浏览器凭据，会被 401 掉——
  这是预期行为。
- **启动自检**：插件加载时会往 `plugin.log` 写一行浏览器半边有没有进客户端模块图，
  例如 `desktop: 浏览器半边已注册 id=dsh-mobile-console rev=…`。它出问题时**不会报错**，
  只是设置里少一页，所以这条日志是排查入口是否存在的第一手证据。

## 配对

配对地址里带一个 128 位随机令牌：`http://<局域网IP>:8799/?k=<令牌>`。

第一次用带 `?k=` 的地址打开时，服务会种一个 `HttpOnly` Cookie 并 302 跳回 `/`，
**把地址栏里的令牌抹掉** —— 免得令牌留在浏览记录、截图或分享出去的链接里。之后靠 Cookie 鉴权。

也可以用 `X-MC-Token` 请求头（脚本、自动化用这个）。

令牌保存在 `$DSH_HOME/dsh-mobile-console/state.json`。删掉它（或删掉整个目录）会重新生成，
**已经配对过的手机需要重新配对**。

## 安全模型

这是个只有你自己用的局域网工具，按这个前提设计：

- **默认什么都不做。** 不武装的会话完全不接管。
- **接管需要两个条件同时成立**：会话已武装 + 至少一台手机在线。
- **令牌是唯一凭据**，128 位随机、`timingSafeEqual` 比较，不接受空令牌，不走 URL 之外的降级路径。
- **没有令牌什么都拿不到**：页面、静态资源、接口、二维码全部 401。
- **Cookie 是 `HttpOnly` + `SameSite=Lax`**，脚本读不到。
- **页面端不做字符串拼 HTML**：会话标题、模型输出、工具参数都是不可信文本，一律用 `textContent` 构建 DOM。
- 服务默认绑 `0.0.0.0`（不然手机连不上），**所以它只适合可信局域网**。
  不要在公共 Wi-Fi 上开，也不要把它转发到公网。

想收紧的话，把 `config.json` 里的 `bindHost` 改成某个具体网卡地址，或在系统防火墙里只放行专用网络。

## 安装

> **想用「设置 → 手机控制台」这一页，必须按下面方式二 / 方式三装成包。**
> 浏览器半边（`client.js`）只认 `name` 是**裸包名**的挂载行；方式一那种 `boot.js` 绝对路径
> 挂载**不会**带上它（DSH 的客户端模块扫描是按包读 `package.json` 的 `dsh.client` 的）。
> 只想要手机网页 / APK、不要设置页的话，方式一最省事。

### 方式一：直接挂本地目录（最快，但**没有设置页入口**）

在 profile 的 `cordis.patch.yml` 末尾追加：

```yaml
- insert:
    - id: dsh-mobile-console
      name: '<项目目录>\plugin\boot.js'
```

### 方式二：装成 profile bundle（推荐，带设置页入口）

```bash
dsh plugin --profile desktop add <项目目录>\plugin
```

等价于做两件事：把包加进 profile 的 `dependencies`（可以是 `file:` / `link:` 本地路径），
再把包名加进 `dsh.profile.bundles`。之后挂载那一行的 `name` 就是**裸包名** `dsh-mobile-console`，
浏览器半边才会跟着加载。

### 方式三：手工改 profile 的 bundles 列表

在 profile 的 `package.json` 里：

```json
{
  "dependencies": { "dsh-mobile-console": "link:<项目目录>/plugin" },
  "dsh": { "profile": { "bundles": ["...", "dsh-mobile-console"] } }
}
```

再让 profile 做一次依赖解析（`dsh plugin` 或 profile 自带的包管理）。

### 防火墙

Windows 第一次监听时可能弹「允许访问」，选**专用网络**。没弹或误点了「取消」的话：

```powershell
New-NetFirewallRule -DisplayName "DSH Mobile Console" -Direction Inbound `
  -Protocol TCP -LocalPort 8799 -Action Allow -Profile Private
```

端口被占用时插件会**自动往后顺延**（最多 10 次），实际端口以 `/mobile status` 或 `plugin.log` 为准。

## 配置与文件

都在 `$DSH_HOME/dsh-mobile-console/`（Windows 下即 `%USERPROFILE%\.dsh\dsh-mobile-console\`）：

| 文件 | 内容 |
| --- | --- |
| `config.json` | 配置，见下表 |
| `state.json` | 令牌 + 每个会话的武装状态 |
| `plugin.log` | 运行日志，1 MB 轮转 |

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `port` | `8799` | 起始端口；被占用会自动顺延 |
| `bindHost` | `0.0.0.0` | 监听地址。`127.0.0.1` 只有本机能连 |
| `relayTimeoutSec` | `120` | 推给手机后等多久没人答就回落 |
| `autoArm` | `false` | 新会话是否自动武装 |
| `maxFeed` | `100` | 动态流保留条数 |

配置在**启动时**读一次；改完要重新加载插件（改 `src/` 下任何文件会自动热重载）。

## 排错

**手机打不开页面**

1. `/mobile status` 看服务是否在跑、端口多少、有没有在线手机。
2. 手机和电脑是不是同一个 Wi-Fi（注意别连到访客网络或有 AP 隔离的网络）。
3. 电脑上先自己打开那个地址试试；能开就是防火墙问题。
4. `plugin.log` 里找 `server: 监听` 那一行，确认 IP 和端口。

**审批还是弹在电脑上**

- `/mobile status` 看这个会话是不是「已武装」。
- 手机页面是不是开着（关掉页面就没有在线手机，插件会主动不接管）。
- `plugin.log` 里找 `relay: 转手机作答`；没有这行就说明没进入接管。

**改了代码没生效**

`boot.js` 会自己盯着 `src/` 和 `ui/` 热重载，**并且复用同一个端口**（重建前先等上一次卸载完成），
所以已经配对好的手机链接不会失效。日志里会看到一次 `plugin unloaded` + `plugin loaded port=<同一个端口>`。
浏览器页面需要刷新一下。

**动态流和武装状态都能扛住重载**：武装状态落在 `state.json`，动态流挂在进程内的共享存储上。
这是踩过坑之后补的——早先动态流是纯内存的，一重载手机页面就空了，连"注入的消息有没有回复"都看不到。

正在等手机作答时如果发生重载，待办会**立刻回落给原生链路**（而不是干等 120 秒），
所以电脑上会正常弹出确认框，回合不会卡住。

**宿主重新挂载时不会留下"幽灵实例"**：宿主重挂载的顺序是**先挂新实例、后卸旧实例**（实测甚至旧的不卸），
早期版本因此出现过"同一个进程同时监听 8799 和 8800、`/mobile` 因重复注册而不可用、手机还连在跑着旧代码的那个端口上"。
现在 `boot.js` 在进程内维护一个实例槽，新实例挂载时会**先把上一个实例收干净**再启动。

> 如果你的 `plugin.log` 里出现过 `命令注册失败 … already registered`，或者看到两个端口同时被监听，
> 说明进程里已经有幽灵实例了——**重启一次 DSH** 即可恢复干净状态（新实例无法回收它之前就存在的旧实例）。
> 注意 `boot.js` 是宿主挂载的入口、会被 ESM 缓存，所以对 `boot.js` 本身的修改也要重启 DSH 才生效。

| `wiring.test.mjs` | 真 `apply()` 装配、真 HTTP、命令输出、卸载、热重载复用端口、**设置页路由**（开关真的启停监听、信任围栏、会话接管、参数校验） |
| `client.test.mjs` | 浏览器半边：ModuleLoader 契约、注册进 `settings.section` 的参数、以及用 React 桩**浅渲染整页**（含关闭态不该出现地址） |

> 装配层的设置页用例是把**插件真实注册到假 webServer 上的那个处理器**抓出来直接驱动的，
> 不是我在测试里另写一份路由逻辑——否则测的是测试自己。它会真的 `POST /enabled` 把监听关掉、
> 确认端口不通，再开回来、确认又能服务。

> 测试里不留「等固定毫秒再断言异步结果」这种写法：`server.test.mjs` 曾经用
> `sleep(30)` 之后断言断开计数归零，机器一忙就偶发失败——那不是产品 bug，是断言在赌时延。
> 现在一律轮询到条件成立（带上限），空闲时立刻过，忙时也不误报。

`qr.test.mjs` 里还有一段**差分比对**：逐模块对照一份参考实现。那份参考实现在仓库之外
（profile 的 `node_modules` 里），随时可能因为 profile 重新解析而消失——已经发生过一次。
所以它现在是「在场才跑，不在场就明确跳过并打印说明」，而不是让整个套件挂掉。
想恢复差分比对时把参考实现放回去，或用 `MC_QR_REFERENCE` 指过去。

还有三个对着**正在运行的 DSH** 做验证的工具：

```bash
node tools/live-check.mjs                  # 体检：鉴权、页面、二维码、SSE
node tools/live-answer.mjs --count 1       # 假装是一台手机，自动代答一条待办
node tools/live-send.mjs --session <id> --text "..."   # 假装是一台手机发消息
```

`live-answer.mjs` 和 `live-send.mjs` 读的是真实令牌，等价于「一台已经配对的手机」，
所以在没有第二台设备时也能验证整条链路。

## 实机验证记录

下面这些是在**真实运行的 DSH** 上跑出来的，不是"应该能用"：

| 能力 | 证据 |
| --- | --- |
| 看状态 | 会话列表实时显示运行中 / 空闲 / 离线、武装状态、最近输出 |
| 审批-允许 | `via=approval tool=pwsh decision=allowed-once`，需要越权的写入**真的执行了**，电脑端无弹窗 |
| 审批-拒绝 | `decision=rejected`，越权写入被拦住、文件没有生成，电脑端同样无弹窗 |
| 回答问题 | 两次真提问分别选「甲」「乙」，都准确回传，回合零打断 |
| 发消息 | 手机注入的消息作为正常用户消息抵达并触发新回合，动态流记为 `sent` |
| 回复回流 | 动态流里出现真实回复文本（`assistant/message` → `turn/end` 这条抽取路径） |
| 令牌鉴权 | 无令牌一律 401；配对链接 302 种 Cookie |
| 热重载 | 连续多次重载都复用在同一个端口，手机链接不失效；动态流不丢 |

## 已知限制

- 只覆盖 `approval/request` 与 `ask_user_question`；别的交互式确认（比如某些工具自带的询问）不走这两条路。
- 手机页面刷新后靠 SSE 重新拿一份完整快照，没有增量同步 —— 快照本身很小，这是刻意的取舍。
- 只绑一个端口、单进程；多开 DSH 时后启动的那个会自动顺延端口，两台机器的配对链接不通用。
- 动的是真实会话：手机上发的消息、批的审批，电脑端立刻可见。
